# Qiita記事：Blendファイルのセキュリティスキャン自動化

## タイトル案
「Blendファイルのセキュリティスキャンを自動化してチーム開発を安全にする」

---

## 想定読者
- インディーゲーム開発チームでBlendファイルを共有している人
- バイナリアセットのセキュリティに課題を感じている人
- GitHub ActionsでCI/CDを構築している人

## 記事の長さ目安
- 必須セクション: 約2,000〜3,000字
- オプション含む全体: 約4,000〜5,000字

## 段落構成

### 1. はじめに
- インディーゲーム開発におけるチーム協業の増加
- Blendファイルなどのバイナリアセット共有の必要性
- 本記事で解決する課題の提示
  - セキュリティリスクの軽減
  - 自動化によるコスト削減

### 2. Blendファイルに潜むリスク
- Blendファイルが実行可能なPythonコードを含める仕組み
  - Text blocks、Driver expressions、App handlers など
- セキュリティリスク（マルウェア的なコード）
- 個人情報リスク（ファイルパス、APIキー、パスワードなど）
- 実際に起こりうるシナリオ例

### 3. 手動チェックの限界 [オプション：短縮可]
- バイナリファイルの中身は目視で確認しにくい
- 人的コストと見落としのリスク
- スケールしない問題

> 短縮する場合：セクション2の末尾に1〜2文で言及

### 4. 解決策：自動スキャンシステムの構築
- 設計方針（コストをかけない自動化）
- 多層防御の考え方
  - Layer 1: ローカル（pre-commit）
  - Layer 2: リモート（GitHub Actions）
- システム構成の概要図

### 5. スキャナーの実装
- Malware Scanner（危険なコードパターン検出）
- Privacy Scanner（個人情報・秘密情報検出）
- 検出レベルの設計（ERROR / WARNING）

#### 5-1. 検出パターンの詳細 [オプション：表で簡潔に]
- ERROR レベル: os.system, subprocess, exec, socket, requests など
- WARNING レベル: eval, 個人パスなど

### 6. GitHub ActionsによるCI統合
- プッシュ・PR時の自動スキャン
- Blenderのキャッシュによる高速化
- 差分のみスキャンする効率化
- ワークフロー設定例（コードブロック）

### 7. Pre-commitによるローカルスキャン [オプション：発展的内容]
- コミット前に検出する利点
  - Git履歴に残る前にブロック
  - 修正コストの削減
- チーム環境の多様性への対応
  - Blenderあり環境 → フルスキャン
  - Blenderなし環境 → 軽量スキャン（検討中）
- セットアップ手順

> 省略する場合：セクション4で「将来的にはpre-commitも検討」と言及

### 8. リスク発見時の対処例
- ケース1：マルウェア検出時
  - 外部からのファイルなら使用中止・提供元に確認
  - 意図的なコードか悪意あるコードかの判断
  - チームへの報告と対応フロー
- ケース2：APIキー・パスワード検出時
  - キーの即時無効化と再発行（ローテーション）
  - Git履歴からの削除（git filter-branch / BFG Repo-Cleaner）
  - 漏洩範囲の確認と影響調査
- ケース3：個人パス（/home/username等）検出時 [オプション]
  - 相対パスへの修正
  - チーム内での命名規約の策定

### 9. 導入手順・使い方 [オプション：別記事化も可]
- ローカルでの使用方法
- CIへの組み込み方法
- クイックスタート（コマンド例）

> 省略する場合：GitHubリポジトリへのリンクで代替

### 10. まとめ・今後の展望
- 本システムで得られるメリット
  - 自動化による省力化
  - セキュリティリスクの早期発見
  - チーム全員が安心してアセット共有
- 今後の改善案
  - 軽量スキャナーの実装
  - 他のバイナリ形式対応（FBX, glTF等）
